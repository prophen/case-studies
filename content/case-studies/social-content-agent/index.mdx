## Where I started

I wanted to start working with AI as an engineer, and I needed help creating social content. My idea was an agent that could create content and post it to a social channel.

I was overly ambitious for a first project. What I built became an AI-assisted workflow: it generates LinkedIn drafts, lets a person review and approve them, and simulates scheduled publication. It does not independently create and post content for me.

Social Content Agent was my first real Next.js app and my starting point for building software with AI integrated.

## How I built the first version

I built the first version with guidance from Perplexity. It gave me the code and instructions for setting up Supabase and Vercel. I followed those instructions to put the app together; I did not write any of the code.

Through that process, I learned about the structure of a Next.js application and the separation between client and server. I still want a deeper understanding of the code and more confidence making additions independently.

</Callout>

## Following the workflow

The application keeps a person involved from the initial topic through approval and scheduling.

<WorkflowSteps>
  <Step title="Generate a starting point">A signed-in user enters a topic. The server combines it with saved brand-voice guidance and calls the OpenAI Responses API. The response returns as editable text.</Step>
  <Step title="Review and approve">The user edits and saves the draft, then approves it. Changing approved content returns it to draft and clears its approval and pending schedule.</Step>
  <Step title="Schedule and track">An approved draft can be scheduled for a future time. A background job marks due drafts as published in the database and adds an activity event. Publication is simulated.</Step>
</WorkflowSteps>

The reviewed version includes per-user brand-voice settings for audience, tone, goals, formatting, and accuracy guidance. Changes to these settings apply to future generations; existing drafts stay as they are.

## Under the surface

Next.js provides the interface and server routes. The browser sends requests to those routes for generation and draft operations. Supabase supplies authentication and stored data, and the OpenAI Responses API supplies generated text.

<ArchitectureDiagram src="/case-studies/social-content-agent/architecture.svg" alt="Application architecture connecting the Next.js interface to generation and draft routes, OpenAI, Supabase, and the simulated publisher." caption="Architecture reconstructed from source at commit c68bd8d. Live deployment behavior has not been verified." width="1000" height="500" description="Authenticated routes handle drafts and brand voice through Supabase and send generation requests to OpenAI. A separate cron route checks a bearer secret and uses a server-side admin client to process due drafts and record publication events. There is no social-network publishing call in that path." />

The generation route checks authentication, validates the topic, and checks recorded usage before calling the model. The database migrations define ownership policies for user data. A separate protected route handles simulated publication.

These are parts of the client/server separation I began learning about through this project. The code review helps make that structure visible, while live integration testing remains outstanding.

## Decisions visible in the code

The later source review identified three implementation choices worth explaining. These observations describe how the code works; they are not a record of decisions I independently designed during the first build.

<Decision title="An edit clears the previous approval" why="Approval applies to the text that was reviewed. When that text changes, the update function returns the item to draft and clears approval and scheduling timestamps." tradeoff="Even an edit to a scheduled post requires another approval and schedule.">
[updateDraft](https://github.com/prophen/social-content-agent/blob/c68bd8d2f28480145c75fcebc7961bc2f97a08d5/lib/drafts.ts) gives content changes precedence over status changes. [Workflow tests](https://github.com/prophen/social-content-agent/blob/c68bd8d2f28480145c75fcebc7961bc2f97a08d5/tests/drafts.test.ts) cover approval revocation and invalid transitions using mocked database queries. Concurrent live edits have not been tested in this review.
</Decision>

<Decision title="History is stored separately from status" why="A draft's status shows where it is now. Separate activity events record actions such as creation, editing, approval, scheduling, and simulated publication." tradeoff="The state update and event write are separate operations. One can succeed while the other fails, leaving a gap in the history.">
The [publisher](https://github.com/prophen/social-content-agent/blob/c68bd8d2f28480145c75fcebc7961bc2f97a08d5/lib/drafts.ts) rechecks scheduled status before updating rows and records events only for rows returned by the update. That reduces duplicate publication events on repeat runs, but does not make the whole operation atomic.
</Decision>

<Decision title="Publication stops at the simulation" why="The publisher updates database state and records activity, so the scheduling workflow can be explored without sending a post to a social network." tradeoff="Real publishing still needs account connection, provider authorization, token handling, and delivery-error handling.">
The [job route](https://github.com/prophen/social-content-agent/blob/c68bd8d2f28480145c75fcebc7961bc2f97a08d5/app/api/jobs/publish-due-drafts/route.ts) requires a configured bearer secret. This describes the smaller scope the app reached; my original ambition included real posting.
</Decision>

The review also found limits to address. The generation quota uses a separate count and recording step, which can weaken enforcement under concurrent requests. At the reviewed commit, the checked-in migrations omitted the approval timestamp column. I confirmed that the field already exists in my hosted database; the gap was in the repository's migration history.

A subsequent maintenance pass added a forward migration for reproducible setup, including approval and automatic modification timestamps. Seven PostgreSQL migration tests cover fresh setup, existing-schema upgrades, record preservation, and draft ownership rules; the complete local suite passes 91 tests. These changes are committed in the repository. This review has not applied them to the hosted database or inspected its existing timestamp triggers, and the tests use a minimal substitute for Supabase's authentication environment.

A [walkthrough is linked in the repository](https://youtu.be/HWN_2BmjthY); its contents and captions still need review.
